# Fascia Identity contract — changelog

Every published version of [identity.v1.yaml](identity.v1.yaml), its schemas and its vectors,
newest first. A host or rail service vendors a copy pinned to a tag and reads this to decide
whether a diff needs its attention.

| Version | Date | Change | Does your client care? |
| --- | --- | --- | --- |
| `0.7.0` | 2026-10-21 | Home areas. A community may name up to 20 official Fascia Places areas as its home area (`setHomeAreas`, signed by its active key); the service checks each with Places and stores its level, name and ancestors. The register entry from `getKeys` gains `areas`. New `listCommunitiesWithin` (`GET /v1/identity/communities?within=`) finds active communities with a home area at or under an area. New codes `areas_invalid`, `area_unknown`, `community_suspended`, `places_unavailable`. | Only if you want to find communities by place, or let a community name its area. `areas` is an addition; a client that ignores it keeps working. |
| `0.6.0` | 2026-10-20 | Rings on credentials. A credential may carry `ring`, set by its issuer: 1, only in the issuing community; 2, in any community the member belongs to; 3, with any community that trusts the issuer. Absent means 1; any other value fails the card. Each credential `/verify` returns gains `ring`. | If you accept credentials: honour the ring (`acceptCredential` in `@fascia/dcp-verify` does, given the receiving community and the memberships presented alongside). If you issue them: set the ring you mean, since none means 1. |
| `0.5.0` | 2026-10-20 | A key belongs to one community: `createCommunity` answers `409 key_in_use` (with `community_ids`) when `first_key` already belongs to a community, so a repeated registration no longer creates a second one, and a handover to a key of another community is refused the same way. States the rule for trust list editions: a list's current edition is the newest document with that list name published by that community, the last match in `listDocuments`, which answers oldest first. | If you register communities or hand over keys, handle `409 key_in_use`; if you follow a trust list by name, the rule is now stated. |
| `0.4.0` | 2026-10-19 | Credential families. A credential schema may name its `family` (`badge`, `rating` or `identity`) and its `w3c_type` (ending in `Credential`); both are checked when present. `listDocuments` returns each credential schema's `family`. | Only if you publish credential schemas or group credentials for display. Both fields are optional additions. |
| `0.3.0` | 2026-10-19 | Credentials. A new claim type, `credential` (command `/fascia/member/credential`, at most 365 days), naming its type by `schema` and pinning it by `schema_hash`; `may_issue_schemas` limits a steward to some types. Communities publish credential schemas, policy profiles and trust lists: `publishDocument`, `listDocuments`, `getDocument`. `/verify` gains `credentials`. New codes `document_malformed`, `document_invalid`, `document_unknown`. Vectors unchanged. | Only if you issue or accept credentials. The new field is an addition; a client that ignores it keeps working. |
| `0.1.0` | 2026-10-16 | First version. Ten endpoints; the four-part `Fascia-Presentation` header with claims carried once as DAG-CBOR and bound by `claims_sha256`; claims as UCAN 1.0 delegations under the Fascia profile; 47 vectors (8 passing, 39 failing). First published version. | n/a |
